# 什么是架构

> 一篇对话归档。
> 关于一个调研者在拆解 Hermes Agent 源码时，被迫停下来问自己的问题。

---

## 0. 引子：为什么停下来了

我正在调研 Hermes Agent——一个多平台、多模型、多记忆形态的 AI Agent 引擎。

为了理解它的结构，我用了一个分层源码图工具（AX-GRAPH）来拆它。Layer 1 给出模块分布和静态耦合，Layer 2 展开隐式簇，Layer 3 画调用路径。三层各管各……

然后我犯了一个错——不，是遇到了一个坎：

> 我想画一张「架构总览图」。
> 但我不知道这张图应该画什么。

我有三个候选方案：
- 在 Layer 2 补几个「架构层 cluster」节点（基于现有 module 聚类）
- 在 Layer 1 用 desc 字段给 module 贴架构标签
- 新建一个 Layer 3 「architecture」功能图

三种方案都能写出来。问题不是「哪个好」，而是**我根本不知道这张图应该表达什么**——

> 我连「架构」是什么都没想清楚，就在讨论怎么画架构图。

这就是这篇文章的起点。停下来，问自己：

> **什么是架构？**

下面是我当时的回答。半年后回头看，它仍然成立。

---

## 1. 三件事

如果把这个问题摊开，**架构是三件事**，不是三张图、不是三个模块划分、不是三种技术选型。

### 1.1 边界：系统内有哪些独立的子系统

第一个问题：**这个系统的边界在哪？**

不是「代码分几个目录」——目录划分只是结果，**边界本身是决策**。

> 例子：Hermes Agent 把飞书、Telegram、Discord、Slack、WhatsApp、22 个平台适配器，**全部塞进 `gateway/` 一个 module**。而不是 `feishu/`、`telegram/`、`discord/` 各开一个目录……

**这是架构决策，不是习惯**。它的内核是：

> 22 个适配器在「和外部世界对接」这件事上是**同一类角色**。
> 类比：一个国家可以有 22 个大使馆，但「外交部」是一个机构。

**为什么要聚在一起？** 因为它们共有的不变量是：「把异构消息转成统一内部 Message」。这个不变量聚 22 个文件也成立，散 22 个目录也成立——但聚在一起，边界才清晰。

**这就是边界**：把具有共同不变量的代码**圈在一起**，让边界外的代码只看到接口、看不到实现。

软件史上对这条最经典的表述来自 Martin Fowler——他在《Patterns of Enterprise Application Architecture》里给出过「分层」（Layer）的概念：

> 把具有相同变化频率、相同抽象层次的代码放在同一层；层与层之间只允许单向依赖。

Fowler 的「层」和上面说的「边界」是同一个意思——**只是 Fowler 给了它一个更可操作的形式**。

### 1.2 责任分配：每个子系统负责什么、不负责什么

第二个问题：**边界画好了，每个子系统负责什么、不负责什么？谁第一个接手、谁不能插手？**

不是「这模块有几个函数」——函数数量只是结果，**责任分配才是架构**。

> 例子：用户发一条飞书消息——
> - `gateway/` 接住，**转成 internal Message 推给 agent**
> - `agent/` 收到，**不知道消息来自飞书还是 CLI**（不关心）
> - `gateway/` 收到 agent 输出，**只负责按原平台格式回发**（不关心 agent 怎么想）

**这就是责任分配**。它的硬约束是：

> - gateway 不能调 agent 的内部状态机——只能推 Message
> - agent 不能识别 platform 名称——只能处理 internal Message
> - 这两个约束一旦违反，架构就被破坏

Simon Brown 给这条起了个名字——**C4 Model**：

> 系统由 **containers** 组成，每个 container 有自己的 **responsibility**；container 之间通过明确的 **relationships** 通信；**绝对不能跨过关系**。

Hermes 的 gateway/agent 责任分配就是 C4 的标准实现——**container 之间的边界由「消息类型」定义，而不是「API 调用关系」**。

### 1.3 不变的东西：5 年后代码全改了，什么还应该成立

第三个问题：**什么是这个系统真正难改的部分？**

这是最难回答的——因为答案藏在 **5 年后**。

> 反例：一个项目的代码组织得很好、模块划分很清晰——但它的「不变」是「业务逻辑」还是「基础设施选型」？如果业务变了代码全得改，那它的架构就白做了。
>
> 正例：Hermes 自己写了两条铁律——
> - 「prompt cache 是神圣的」——任何改动必须保持 cache locality
> - 「core 是窄腰」——LLM 在中间，22 个平台在边缘

这两条不是技术选型，是**宪法**。明天 Hermes 用 Rust 重写、后天用 WASM 跑——

> 「LLM 在中间、平台在边缘」这个架构依然成立。

Robert C. Martin 在《架构整洁之道》里把这条推到极致：

> 架构 = **用最小成本应对变化**。
>
> 「好架构」的标志是：**业务规则不知道、不关心 UI 用什么、数据库用什么、网络协议用什么**——但「业务规则」必须知道自己在做什么。
>
> 这就是「六边形架构」「洋葱架构」「干净架构」想表达的事——**把「变化得慢的」放在中心，把「变化得快的」放在边缘**。

**Hermes 的窄腰就是这个原则的具象化**——LLM 是变化得慢的（在中间），平台/UI/工具是变化得快的（在外圈）。

## 2. 三个误解

上面的三件事回答「架构是什么」。下面这三个误解回答「**架构不是什么**」——而且**每一个我都犯过**。

### 2.1 误解 1：架构 = 模块划分

**真相**：模块划分是「代码组织」，架构回答的是「为什么这样组织」。

我犯这个错时是这样：拆 Hermes 源码 → 看到 `gateway/`、`agent/`、`tools/`、`providers/`……→ 在脑子里得出「哦，Hermes 是按角色分的」。**这句话对，但不是结论。**

架构是：**为什么 gateway 是 1 个 module、不是 22 个？**——因为 22 个平台共享「转 internal Message」这个不变量。**这才是架构。**

### 2.2 误解 2：架构 = 技术选型

**真相**：技术选型是「用什么」，架构是「为什么用这个不用那个」。

「Hermes 用 SQLite 做记忆、FastAPI 做服务、asyncio 做并发」——这是技术选型。
「**Hermes 必须把所有外部交互（22 平台 + 1 CLI）都收口到 gateway，是因为需要统一事务边界**」——这是架构。

技术选型变了架构还在；架构变了**所有技术选型都得重做**。

### 2.3 误解 3：架构 = 画图

**真相**：图是描述架构的工具，**架构本身是约束和决策的集合**。

我刚才犯的就是这个错——「想画架构图」但不知道画什么。**因为架构图不是「更好的图」，是「对架构决策的精确表达」**。

图漂亮但架构错——白搭。
图丑但架构对——能用。

> 一个反直觉的检验标准：**如果一张图把项目名擦掉后仍然成立，它就画对了；如果换成别的项目也能套上去，它就画错了**。

我后来画的 Layer 1「模块分布 + 静态耦合」图——**擦掉 Hermes 这个名字，套到 LangChain、LlamaIndex、AutoGPT 都成立**。**说明那张图画的是「所有 AI Agent 引擎的共性」，不是 Hermes 的架构**。

## 3. 回到 Hermes：用这套框架看

上面是抽象。**下面这套框架在 Hermes 上具体长什么样**——这不是教你怎么画架构图，是**用架构的眼睛看代码**。

### 3.1 边界

Hermes 的边界在哪里？

按「模块是不是一个独立子系统」切——12 个 module，但不是每个 module 都有「共同不变量」：

| Module | 共同不变量 | 是子系统吗 |
|---|---|---|
| `hermes_cli` | **被全库 import 970 次**——是「其他一切」的基础 | 是 |
| `agent` | 引擎核心，所有 model/tool 调用收敛到这里 | 是 |
| `gateway` | 22 个平台共享「转 internal Message」 | 是 |
| `tools` | 工具抽象层 | 是 |
| `providers` | 提供商元数据 + 路由 | 是 |
| `tui_gateway` | TUI 与 backend 的协议桥 | 是 |
| `acp_adapter` | Agent Client Protocol 适配 | 是 |
| `plugins` / `cron` | 可选能力 | 是 |
| `apps` / `ui-tui` / `web` | 用户面前的前端 | 是 |
| `infra` (6 个工具件) | 横切基础��施——**不是子系统，是「横切关注点」** | 否 |

**最后一个观察是关键**：infra（logging/time/bootstrap/utils...）**在 module 层面是个目录，但在架构层面是「横切关注点」**。Layer 1 Graph 把它们归为 `infra`——只是在 module 分布上做了统计归类，不能因此把它们当成一个独立子系统。

### 3.2 责任分配

Hermes 的责任分配硬约束：

```
外部消息 → [gateway/] → 统一 internal Message
                          ↓
                       [agent/]   ←—— 不识别 platform 名字
                          ↓
                    internal Response
                          ↓
外部消息 ← [gateway/] ← 统一 internal Message
```

**关键约束**：
- `gateway/` **不**能读 agent 状态机
- `agent/` **不**能 import 任何 platform-specific 库
- 任何 platform-specific 异常必须**在 gateway 层被翻译成统一错误**，否则污染下游

**如果有人哪天提交一个 PR 让 `agent/` 直接 import `feishu_sdk`——这 PR 不是 bug，是架构事故**。

### 3.3 不变的东西

Hermes 自己写了两条铁律——这才是 Hermes 的「宪法」：

1. **「prompt cache 是神圣的」**——任何代码改动必须保持 cache locality（即 prompt token 的相对顺序、prefix 结构稳定）。
2. **「core 是窄腰」**——LLM 在中间，22 个平台在边缘，业务规则在内层，技术细节在外层。

这两条不是「现在的代码是这样」——**是「5 年后还应该这样」**。

如果哪天有人要重写 Hermes，他应该：
- **保留**：prompt cache 不变量、core 窄腰、gateway/agent 责任分配
- **可以重写**：Python 换成 Rust、SQLite 换成 Postgres、asyncio 换成 Tokio——**这些都只是技术选型，不是架构**

**「好架构」就是把「变与不变」分得清清楚楚**。

## 4. 另一个维度：架构是蓝图

前面用「三件事」回答了「架构是什么」。那是一种视角，但不是唯一的视角。

软件工程里还有一种更经典的表达：

> 软件架构 = **组件（Components） + 连接件（Connectors） + 约束与原则（Constraints & Principles）**。
>
> 如果把软件系统比成一栋摩天大楼，组件就是砖块、钢筋、玻璃；连接件就是梁、走廊、电梯井；约束与原则就是结构规范——承重墙不能拆、消防通道必须通畅。

这个视角不回答「架构为什么难」，它回答的是**「架构从高处看是什么样子」**。

### 4.1 组件：系统的基本构建单元

组件是系统中**可以独立识别**的功能块。它不一定是目录、不一定是类、不一定是服务——它是在架构讨论中「可以被点名」的实体。

在 Hermes 里：
- `gateway/` 是一个组件
- `agent/` 是一个组件
- `tools/`、`providers/`、`hermes_cli/` 都是组件

但注意：**组件不是 module 的同义词**。`infra/` 虽然在 module 层面存在，但在架构层面不被看作一个独立子系统——它是横切关注点，被其他组件共享。模块划分只是组件的**一种可能表达形式**。

### 4.2 连接件：组件之间如何交互

连接件定义组件间交换什么、怎么交换、遵循什么协议。

在 Hermes 里，gateway 和 agent 之间的连接件不是「函数调用」，而是 **internal Message 这个数据结构**：

```
gateway --(internal Message)--> agent
agent   --(internal Response)--> gateway
```

这个数据结构就是连接件的具体化。它的力量在于：只要 Message 格式不变，gateway 和 agent 可以各自独立演化。连接件越稳定，组件越容易替换。

### 4.3 约束与原则：哪些规则不能违反

约束是架构的「硬边界」，原则是架构的「设计风格」。

Hermes 的约束：
- `agent/` 不能 import 任何 platform-specific 库
- gateway 不能直接读写 agent 的状态机
- 任何改动必须保持 prompt cache locality

Hermes 的原则：
- core 是窄腰
- 业务规则在内层，技术细节在外层
- 变化得慢的放中心，变化得快的放边缘

约束告诉你**什么不能做**，原则告诉你**应该往哪个方向做**。两者合起来，就是架构的「宪法」。

### 4.4 核心作用

蓝图视角强调架构的三个核心作用：

1. **控制复杂性**：当系统变大时，通过组件划分把全局复杂度切分到局部。你不需要同时理解所有代码，只需要理解你负责的那个组件以及它对外暴露的连接件。
2. **保障非功能性需求**：高可用、可扩展、可维护、安全性……这些不是某一行代码写对的，而是组件与连接件的设计带来的系统级属性。
3. **团队沟通基础**：架构图、接口文档、设计评审，本质上都是围绕组件、连接件和约束达成共识的工具。

这也是为什么那么多人把架构比作「蓝图」：蓝图不是给施工队看热闹用的，它是所有人对齐目标、分工协作的契约。

### 4.5 常见模式

蓝图视角把架构总结出几种经典模式：

| 模式 | 核心思想 | 适合场景 |
|---|---|---|
| **分层架构** | 按抽象层次划分组件，层之间单向依赖 | 企业应用、Web 后端 |
| **微服务架构** | 按业务能力拆分组件，每个组件独立部署 | 大型团队、异构技术栈 |
| **事件驱动架构** | 组件通过事件异步解耦 | 高并发、流式处理、长链路业务 |
| **六边形/洋葱/干净架构** | 核心业务在中心，外部技术细节在边缘 | 需要长期演化的业务系统 |

Hermes 的 core 窄腰，本质上就是**六边形架构**的一个变体：LLM 和业务规则在中央，平台、UI、工具通过 gateway、tools、web 等适配器接入。模式不是教科书里的 diagrams，而是你手中的组件、连接件、约束组合出来的结构。

### 4.6 蓝图视角 vs. 三件事视角

这两个视角不是二选一，而是**同一枚硬币的两面**：

- **三件事视角**回答的是：「架构是为了应对变化所做的决策」。
- **蓝图视角**回答的是：「这些决策落在系统里，会变成哪些组件、哪些连接、哪些约束」。

你可以把三件事理解为「为什么」，把蓝图理解为「是什么」。

> 没有「为什么」的蓝图，容易变成一张漂亮的图但缺少灵魂；
> 没有「是什么」的三件事，容易变成正确的口号但落不了地。

所以画架构图的时候，最好同时问自己：
1. 这张图表达了哪些**组件**？
2. 它们之间用什么**连接件**交互？
3. 有哪些**约束和原则**被图形化了吗？
4. 这些组件和约束背后，对应了哪些**边界、责任和不变量**？

如果四个问题都能回答，这张图才不只是「画」，而是「架构」。

## 5. 结尾：三件事与一张蓝图

边界、责任分配、不变的东西——这 3 件事**不是并列关系**，是**相互决定**的：

> - **边界**画错了 → 责任分配失效（gateway/agent 不清，agent 直接 import 平台 SDK）
> - **责任分配**不清 → 不变的东西被掩盖（不知道「哪条规则 5 年不变」）
> - **不变的东西**没找到 → 边界和责任分配都是临时方案（业务一变就重写）

现在又多了第四样东西：**蓝图**。它把前三件事翻译成更具体的架构语言——组件、连接件、约束与原则。反过来，组件画得对不对，也要拿三件事去检验。

**架构不是「画一张图」**——架构是**「持续回答这 3+1 个问题」**：
1. 这条改动是否破坏了**边界**？
2. 这条改动是否重新分配了**责任**？
3. 这条改动是否改变了**5 年后还应该成立的东西**？
4. 这条改动是否违反了某个**组件职责或连接件契约**？

任何一个答「是」，就是**架构级改动**——**需要架构 review，不是普通 code review**。
