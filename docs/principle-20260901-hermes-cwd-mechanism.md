# Hermes 如何记住"当前工作目录"：一个状态，三层存储

> agent 原理系列·第二篇（上下文专题）。本文讲机制，不做源码逐行分析；源码导航附文末。

## 问题：一个被多方依赖的易失状态

Agent 连续干活时，"现在在哪个目录"是个必须随时准确的状态：

- 下一条 shell 命令要在那个目录执行
- `read_file("foo.py")` 的相对路径要按它解析
- 代码执行（code-exec）的子进程要在它里面跑

这个状态有三个麻烦属性：

1. **会变**：Agent 随时可能 `cd` 到别处
2. **会死**：进程退出后，内存里的值就没了
3. **要共享**：一个进程里有多个模块、还有子进程，都要读到它

三个属性分别逼出一个存储。这就是 Hermes 的答案：**同一个值，按三个生命周期各存一份**。

## 结论一句话

Hermes 用三层存储记住 cwd：

- **内存字典**（会话活体）：每条 terminal 命令完成后更新，给"下一条命令"用
- **SQLite 列**（跨进程档案）：会话创建时写起点目录，给"会话恢复"用
- **环境变量**（进程内广播）：入口点更新，给所有模块和子进程读

## 三个存储各管一段生命周期

### 1. 内存字典：会话的"活体"状态

- **存哪**：terminal 工具模块内的进程级字典，以会话为键。多会话并行时各记各的，互不干扰
- **什么时候写**：每条 terminal 命令**成功完成**时。shell 的 `cd` 生效后，解析命令结束时的目录，写回本会话的记录
- **什么时候读**：下一条命令决定默认目录时。优先级：命令显式 `workdir` 参数 > 本会话记录 > 配置默认（`terminal.cwd`，默认是启动目录）
- **生命周期**：进程内。退出即焚，无所谓——下面两层兜底

三个例外，不写记录：

- 命令带了 `workdir` 参数：临时借道，不污染会话的持久目录
- 命令超时/被杀，没报告结束目录：防止把别的会话的目录错记进来
- 非 terminal 工具（文件读写不改变目录，没有记录义务）

### 2. SQLite 列：会话的"档案"

- **存哪**：会话库（state.db）的 sessions 表，cwd 是会话记录的一列元数据
- **什么时候写**：会话创建/延续时，写**起点目录**
- **什么时候读**：`hermes --resume` 恢复会话时，读出来 `chdir` 回去，并同步环境变量
- **语义**："这个会话从哪来"。中途 `cd` 一万次也不落库——恢复时回到起点目录，不是上次 `cd` 的位置
- **为什么是 SQLite**：会话记录本来就在那里，cwd 只是搭车的一列，不为它引入新存储

### 3. 环境变量：进程内"广播"

- **存哪**：进程级全局环境变量 `TERMINAL_CWD`
- **什么时候更新**：入口点——启动时从配置桥接、恢复会话时、切换 worktree 时、cron 任务临时设/还原
- **谁在读**：相对路径解析（file_tools）、代码执行工具、shell 包装器
- **为什么必须用环境变量而不是 Python 全局变量**：**读者里有子进程**。shell 和 code-exec 是独立进程，Python 全局字典过不去；环境变量是唯一自动继承的通道（子进程 fork 时自动拷贝父进程的全部 env）

## 写入时机：不是"每次交互"，是"每条命令"

"交互"（用户说一句话）和"命令"（Agent 执行的一条 shell）是两个粒度。一轮交互里 Agent 可能跑好几条命令，每条成功完成的命令都会更新内存字典；SQLite 和环境变量是低频写。

三层各自的频率：

| 层 | 写频率 | 服务谁 |
|---|---|---|
| 内存字典 + 环境对象 | 每命令（带三个例外） | 下一条命令从哪跑 |
| SQLite 列 | 每会话一次（创建/延续） | 跨进程恢复 |
| 环境变量 | 每入口点一次 | 所有模块和子进程的坐标 |

## 为什么这么设计：三个取舍

1. **每命令写数据库太贵**。即时需求只有"下一条命令从哪跑"，内存字典就够；SQLite 只服务"跨进程恢复"这种低频场景
2. **广播只需要入口点级更新**。文件工具读的是"当前坐标"，不是流水账；坐标在入口点对整齐即可
3. **状态所有权从"共享"收归"私有"**（历史教训）。早期 cwd 存在共享环境对象上（环境跨会话复用），两个会话并行时 A 的 `cd` 会污染 B 的命令默认目录——这是 wrong-worktree 一类 bug 的根源。新代码把 cwd 按会话键记进内存字典，所有权归会话，共享环境只做兜底

## 与 Kimi Code 的对比：锚定 vs 漂移

Kimi Code 是**项目锚定型** Agent：启动目录 = 项目，整个 Agent 的世界就是那个仓库，cwd 几乎不需要"记住"——它不会漂移。

Hermes 是**通用型** Agent：今天在 `~/projects` 写脚本，明天去 `/tmp` 改配置，不换人。cwd 是可漂移的**工具级状态**，漂移才产生"记住"问题。三层机制本质是给"会漂移的锚"配了一套跟踪系统：命令级记录（活体）、会话级存档（档案）、进程级广播（共享坐标）。

## 对自研 Agent 的启示：状态分层的通用模式

任何"Agent 需要记住的易变状态"都可以按这套分层设计：

- **活体**（内存，命令/轮次级）：快、私密、高频写
- **档案**（持久化，会话级）：慢、低频写、跨进程存活
- **广播**（共享通道，入口级）：给"别人"（其他模块、子进程）读的公共坐标

判断一个状态该放哪层，问三个问题：**谁会读它？要活多久？多久变一次？**

- 只活在本进程、要高频读 → 内存
- 要跨进程/跨重启 → 持久化
- 要被其他模块和子进程消费 → 共享通道

V2 的 session_manager 已有类似的分层直觉：会话"存在"的定义 = 文件（档案）+ 索引（活体），延迟持久化——第一条真实消息才落盘。cwd 机制是同一模式的完整工业版。
